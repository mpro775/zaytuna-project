## 1. الملخص التنفيذي

الزيتون سوفت هو نظام SaaS لإدارة محلات الإلكترونيات والأنشطة التجارية الصغيرة والمتوسطة، يركز في نسخة MVP على ربط العمليات اليومية الأساسية في مسار واحد موثوق:

```txt
الإعدادات → المنتجات → المخزون → البيع POS → الدفع → المحاسبة → التقارير → النسخ الاحتياطي → المزامنة المحدودة
```

هذه الوثيقة تحدد ما يجب أن يفعله النظام وظيفيًا وتقنيًا حتى يمكن اعتباره نسخة MVP قابلة للتجربة الحقيقية. لا تهدف هذه الوثيقة إلى بناء ERP كامل، بل إلى توثيق نسخة عملية منضبطة يمكن تشغيلها، اختبارها، وتسليمها داخليًا ثم تجربتها عند متطوعين أو محلات محدودة.

---

## 2. هدف الوثيقة

تهدف هذه الوثيقة إلى:

1. تثبيت المتطلبات الرسمية للـ MVP.
2. منع التوسع غير المنضبط في النطاق.
3. توحيد فهم فريق التطوير والاختبار والإدارة.
4. تحويل المتطلبات إلى GitHub Issues وTest Cases لاحقًا.
5. تحديد معايير قبول كل موديول.
6. توضيح العلاقات بين البيع والمخزون والمحاسبة والعملات.
7. جعل المشروع قابلًا للمراجعة والتسليم.

## 3. نطاق النظام

### 3.1 داخل نطاق MVP

يدخل في نطاق MVP:

1. المصادقة وإدارة المستخدمين.
2. الأدوار والصلاحيات RBAC.
3. إعدادات الشركة والنظام والأمان والنسخ الاحتياطي.
4. العملات وأسعار الصرف.
5. الفروع والمخازن.
6. التصنيفات والمنتجات والمتغيرات.
7. صور المنتجات وشعار الشركة عبر Storage.
8. إدارة المخزون والحركات والتنبيهات.
9. العملاء.
10. الموردون والمشتريات.
11. نقطة البيع POS.
12. فواتير البيع والمدفوعات.
13. المرتجعات وCredit Notes.
14. المحاسبة الأساسية GL.
15. التقارير ولوحة المعلومات.
16. الإشعارات الداخلية.
17. Offline/Sync محدود.
18. النسخ الاحتياطي الأساسي.
19. Audit Logs للعمليات الحساسة.
20. واجهة Frontend مرتبطة بـ Backend حقيقي بدون Mock في الشاشات الأساسية.

### 3.2 خارج نطاق MVP

لا يدخل في MVP:

1. نظام ERP كامل.
2. إدارة الموارد البشرية HR.
3. الرواتب Payroll.
4. CRM خارجي متقدم.
5. تطبيقات موبايل أصلية iOS/Android.
6. ذكاء اصطناعي متقدم.
7. تكامل WhatsApp/SMS تسويقي.
8. بوابات دفع خارجية معقدة.
9. نظام اشتراكات SaaS وفوترة عملاء المنصة بشكل متقدم.
10. BI متقدم أو Data Warehouse.
11. ضرائب متعددة معقدة ما لم يقرر الفريق إدخالها لاحقًا بوثيقة منفصلة.
12. Multi-tenant متقدم ومعزول بالكامل إذا لم يكن مثبتًا في تصميم MVP.

## 4. التعريفات والمصطلحات

| المصطلح | التعريف |
|---|---|
| MVP | نسخة الحد الأدنى القابل للتجربة العملية، وليست المنتج التجاري النهائي. |
| POS | شاشة نقطة البيع التي يستخدمها الصراف لإتمام البيع. |
| GL | General Ledger، دفتر الأستاذ العام أو المحاسبة الأساسية. |
| RBAC | التحكم بالوصول بناءً على الأدوار والصلاحيات. |
| PWA | تطبيق ويب تقدمي يمكنه دعم بعض قدرات Offline. |
| Offline Sale | عملية بيع تحفظ محليًا عند انقطاع الاتصال وتنتظر المزامنة. |
| Pending Sync | حالة عملية محلية لم يقبلها السيرفر بعد. |
| Credit Note | إشعار دائن ينتج من عملية مرتجع أو تصحيح مالي. |
| Base Currency | العملة الأساسية التي تعتمد عليها التقارير المالية. |
| Exchange Rate | سعر الصرف المحفوظ وقت العملية المالية. |
| Audit Log | سجل مراجعة يوضح من نفذ العملية ومتى وما الذي تغير. |
| Mock Data | بيانات وهمية للاختبار لا تعتمد على Backend حقيقي. |

## 5. المستخدمون والأدوار

### 5.1 أدوار المستخدمين المستهدفة

| الدور | الوصف | الهدف الأساسي |
|---|---|---|
| مدير النظام | يملك صلاحيات الإعداد والتحكم الكامل | إعداد الشركة، المستخدمين، الصلاحيات، النسخ الاحتياطي |
| صاحب المحل / المدير | يتابع التشغيل والنتائج | معرفة المبيعات، الربح، المخزون، المديونيات |
| الصراف / البائع | ينفذ عمليات البيع اليومية | بيع سريع، فاتورة واضحة، دفع |
| مسؤول المخزون | يدير الكميات والحركات | إدخال مخزون، تعديل، تحويل، متابعة النواقص |
| المحاسب | يراجع الأثر المالي | قيود، أرصدة، ميزان مراجعة، ربح وخسارة |

### 5.2 مبادئ الصلاحيات

1. لا يسمح لأي مستخدم بتنفيذ عملية خارج صلاحياته.
2. كل عملية مالية أو مخزنية حساسة يجب أن تسجل في Audit Log.
3. العمليات المحاسبية المنشورة لا تعدل مباشرة، بل تعكس بقيد عكسي.
4. صلاحيات الرؤية والتعديل يجب أن تكون منفصلة.
5. يمكن دعم wildcard permissions مثل `products.*` إذا كانت منفذة بشكل صحيح.

---

## 6. الافتراضات العامة

1. النظام يعمل كمنصة ويب SaaS.
2. قاعدة البيانات الأساسية PostgreSQL.
3. Backend مبني على NestJS وPrisma.
4. Frontend يعمل كتطبيق ويب/PWA.
5. التخزين الخارجي للصور والملفات يتم عبر R2 أو S3-compatible provider.
6. العمل Offline محدود وليس بديلًا كاملًا عن السيرفر.
7. المحاسبة في MVP أساسية وليست نظام ERP محاسبي كامل.
8. العملة الأساسية واحدة، ويمكن التعامل بعملات متعددة في الفواتير والمدفوعات.
9. الفواتير القديمة لا تتأثر بتغير أسعار الصرف اللاحقة.
10. الشاشات الأساسية في MVP يجب أن تعمل بدون Mock.

# 8. المتطلبات الوظيفية Functional Requirements

## 8.1 المصادقة Auth

### FR-AUTH-001 — تسجيل الدخول

**الأولوية:** P0  
**الوصف:** يجب أن يسمح النظام للمستخدم بتسجيل الدخول باستخدام بيانات معتمدة.

**المتطلبات:**

- يقبل النظام البريد الإلكتروني أو اسم المستخدم حسب التصميم المعتمد.
- يتحقق النظام من كلمة المرور بشكل آمن.
- يرجع النظام access token وربما refresh token إذا كان معتمدًا.
- يمنع الدخول عند تعطيل المستخدم.
- يسجل محاولات الدخول الفاشلة في Audit/Security Log عند الحاجة.

**معايير القبول:**

- يستطيع مستخدم صحيح تسجيل الدخول.
- لا يستطيع مستخدم معطل الدخول.
- لا تظهر تفاصيل حساسة عند فشل الدخول.

---

### FR-AUTH-002 — تسجيل الخروج

**الأولوية:** P0  
**الوصف:** يجب أن يستطيع المستخدم تسجيل الخروج وإنهاء جلسته.

**معايير القبول:**

- يتم إلغاء صلاحية الجلسة أو refresh token إن كان النظام يدعمه.
- بعد الخروج لا يستطيع المستخدم الوصول للصفحات المحمية إلا بتسجيل دخول جديد.

---

### FR-AUTH-003 — المستخدم الحالي Current User

**الأولوية:** P0  
**الوصف:** يجب أن يوفر النظام endpoint يعيد بيانات المستخدم الحالي وصلاحياته.

**معايير القبول:**

- يرجع بيانات المستخدم الأساسية.
- يرجع الدور أو الأدوار.
- يرجع الصلاحيات الفعالة.

---

### FR-AUTH-004 — تجديد الجلسة Refresh Token

**الأولوية:** P1  
**الوصف:** إذا اعتمد النظام refresh token، يجب أن يستطيع تجديد access token بطريقة آمنة.

**معايير القبول:**

- لا يقبل refresh token منتهي أو ملغى.
- يمكن إلغاء كل الجلسات عند تغيير كلمة المرور أو تعطيل المستخدم.

---

## 8.2 المستخدمون والأدوار والصلاحيات

### FR-USER-001 — إدارة المستخدمين

**الأولوية:** P0  
**الوصف:** يجب أن يستطيع مدير النظام إدارة المستخدمين الأساسيين.

**المتطلبات:**

- إضافة مستخدم.
- تعديل بيانات مستخدم.
- تعطيل/تفعيل مستخدم.
- إعادة تعيين كلمة المرور بطريقة آمنة.
- ربط المستخدم بدور أو أكثر حسب التصميم.

**معايير القبول:**

- لا يمكن حذف مستخدم له عمليات مالية بطريقة تكسر السجلات.
- المستخدم المعطل لا يستطيع تسجيل الدخول.

---

### FR-RBAC-001 — إدارة الأدوار

**الأولوية:** P0  
**الوصف:** يجب أن يدعم النظام أدوارًا قابلة للإدارة.

**الأدوار الأساسية:**

- Admin.
- Manager.
- Cashier.
- Inventory Manager.
- Accountant.

**معايير القبول:**

- يمكن إنشاء دور.
- يمكن تعديل صلاحيات الدور.
- لا يمكن حذف دور مستخدم في حسابات حرجة إلا بعد معالجة الاعتمادات.

---

### FR-RBAC-002 — الصلاحيات

**الأولوية:** P0  
**الوصف:** يجب أن يمنع النظام الوصول غير المصرح به للعمليات.

**أمثلة صلاحيات:**

```txt
products.read
products.create
products.update
inventory.adjust
sales.create
sales.confirm
returns.create
returns.approve
purchasing.create
accounting.read
accounting.journal.post
settings.update
backup.create
sync.manage
```

**معايير القبول:**

- المستخدم بلا صلاحية لا يستطيع تنفيذ العملية.
- تظهر رسالة خطأ واضحة عند منع الوصول.
- wildcard permission مثل `products.*` تعمل إن تم اعتمادها.

---

### FR-SET-004 — إعدادات النسخ الاحتياطي

**الأولوية:** P0

**معايير القبول:**

- لا يستطيع تنفيذ النسخ إلا المستخدم المخول.

## 8.4 العملات وأسعار الصرف

### FR-CUR-001 — إدارة العملات

**الأولوية:** P0  
**الوصف:** يجب أن يدعم النظام إضافة وتعديل وتفعيل وتعطيل العملات.

**الحقول:**

- كود العملة.
- اسم العملة.
- الرمز.
- عدد المنازل العشرية.
- حالة التفعيل.
- هل هي العملة الأساسية؟
- هل هي العملة الافتراضية؟

**معايير القبول:**

- لا يمكن تعطيل عملة مستخدمة في عمليات حرجة إلا بقيود واضحة.
- يجب وجود عملة أساسية واحدة فقط.

---

### FR-CUR-002 — أسعار الصرف

**الأولوية:** P0  
**الوصف:** يجب أن يسمح النظام بإضافة سعر صرف بين العملة والعملة الأساسية.

**المتطلبات:**

- إضافة سعر صرف.
- معرفة آخر سعر صرف.
- استخدام السعر وقت العملية.
- حفظ السعر داخل الفاتورة أو الدفعة.

**معايير القبول:**

- لا تتم فاتورة بعملة غير أساسية بدون سعر صرف صالح.
- لا تتغير الفواتير القديمة عند تعديل سعر الصرف لاحقًا.

---

### FR-CUR-003 — التحويل بين العملات

**الأولوية:** P1  
**الوصف:** يجب أن يدعم النظام endpoint أو خدمة لحساب قيمة مبلغ بعملة أخرى.

**معايير القبول:**

- تظهر القيمة بالعملة الأصلية والعملة الأساسية.
- يتم تقريب الأرقام حسب إعدادات العملة.

---

## 8.6 التصنيفات والمنتجات والمتغيرات

### FR-CAT-001 — إدارة التصنيفات

**الأولوية:** P0  
**الوصف:** يجب أن يسمح النظام بإدارة تصنيفات المنتجات.

**المتطلبات:**

- إضافة تصنيف.
- تعديل تصنيف.
- تفعيل/تعطيل تصنيف.
- دعم تصنيف أب/فرعي إن كان منفذًا.

---

### FR-PROD-001 — إدارة المنتجات

**الأولوية:** P0  
**الوصف:** يجب أن يسمح النظام بإضافة وتعديل وتعطيل المنتجات.

**الحقول الأساسية:**

- الاسم.
- الوصف.
- التصنيف.
- SKU.
- Barcode.
- سعر البيع.
- الحالة.
- هل يتتبع بالمخزون؟

**معايير القبول:**

- لا يمكن تكرار SKU أو Barcode إذا كانا معرفين كحقول فريدة.
- المنتج المعطل لا يظهر في POS افتراضيًا.

---

### FR-PROD-002 — متغيرات المنتج Product Variants

**الأولوية:** P0  
**الوصف:** يجب أن يدعم النظام متغيرات المنتج عند الحاجة.

**أمثلة:**

- اللون.
- السعة.
- المقاس.
- نسخة الجهاز.

**معايير القبول:**

- يمكن ربط المخزون بالمتغير لا بالمنتج العام فقط.
- يمكن البحث عن المتغير في POS.

---

### FR-PROD-003 — البحث والتصفية

**الأولوية:** P0  
**الوصف:** يجب أن يوفر النظام بحثًا سريعًا عن المنتجات.

**طرق البحث:**

- الاسم.
- SKU.
- Barcode.
- التصنيف.
- الحالة.

---

### FR-PROD-004 — IMEI/Serial

**الأولوية:** P1  
**الوصف:** يجب أن يراعي النظام حاجة محلات الإلكترونيات لتتبع السيريال أو IMEI لبعض المنتجات.

**نطاق MVP:**

- يمكن إدخال السيريال عند البيع أو عند المخزون إذا كان منفذًا.
- إذا لم يكتمل التتبع التفصيلي، يجب ألا يعطل رحلة البيع الأساسية.

---

## 8.7 التخزين والملفات والصور

### FR-STO-001 — رفع الملفات

**الأولوية:** P0  
**الوصف:** يجب أن يدعم النظام رفع الملفات المسموحة إلى مزود تخزين خارجي.

**أنواع الملفات في MVP:**

- صور المنتجات.
- شعار الشركة.

**معايير القبول:**

- يتحقق النظام من نوع الملف وحجمه.
- لا يسمح برفع ملفات تنفيذية أو خطرة.
- تحفظ metadata للملف في قاعدة البيانات.

### FR-SALES-002 — تأكيد الفاتورة

**الأولوية:** P0  
**الوصف:** عند تأكيد الفاتورة يجب أن تتم العمليات المترابطة داخل transaction واحدة.

**التدفق المطلوب:**

```txt
Validate Stock
Apply Exchange Rate
Confirm Invoice
Deduct Stock
Create Payment if provided
Create Journal Entries
Create Audit Log
Create Notification if needed
Commit Transaction
```

**معايير القبول:**

- إذا فشل أي جزء يتم rollback كامل.
- لا توجد فاتورة مؤكدة دون أثر مخزني صحيح.
- لا توجد فاتورة مؤكدة دون أثر محاسبي إذا كان نوع العملية يتطلب ذلك.

---

### FR-SALES-003 — المدفوعات

**الوصف:** يجب أن يدعم النظام تسجيل المدفوعات على الفواتير.

- نقد.
- آجل/ذمم للعملاء.
- طريقة أخرى يدوية إذا قرر الفريق ذلك.

**خارج MVP أو P2:**

- بوابات دفع خارجية.
- استرداد بطاقة آلي.

**معايير القبول:**

- الفاتورة المدفوعة كليًا تصبح Paid.
- الفاتورة المدفوعة جزئيًا تصبح Partially Paid.
- الفاتورة غير المدفوعة تصبح Unpaid أو Credit.

## 8.13 المحاسبة الأساسية GL

**الأولوية:** P0

**معايير القبول:**

- لا يمكن نشر قيد غير متزن.

**معايير القبول:**

## 8.16 Offline / Sync

**الأولوية:** P0

**معايير القبول:**

- يمكن عرض حالة آخر مزامنة.

---

### FR-SYNC-002 — حفظ العمليات محليًا

**الأولوية:** P0  
**الوصف:** عند انقطاع الاتصال، تحفظ بعض العمليات محليًا بنطاق محدود.

**نطاق MVP:**

**معايير القبول:**

### FR-SYNC-003 — إرسال العمليات للسيرفر

**معايير القبول:**

- إذا أرسل نفس الطلب مرتين لا ينشئ فاتورتين.

**سياسة MVP المقترحة:**

- السيرفر هو مصدر الحقيقة.
- إذا لم يكف المخزون عند المزامنة، ترفض العملية أو تتطلب مراجعة مدير.

# 11. المتطلبات غير الوظيفية Non-Functional Requirements

## 11.1 الأداء

| المطلب | الأولوية | معيار القبول |
|---|---|---|
| NFR-PERF-001 | P0 | فتح شاشة POS بسرعة مقبولة في بيئة متوسطة. |
| NFR-PERF-002 | P0 | البحث عن منتج في POS لا يسبب تأخيرًا مزعجًا. |
| NFR-PERF-003 | P0 | إنشاء فاتورة بيع يتم خلال زمن عملي مناسب للمحل. |
| NFR-PERF-004 | P1 | التقارير الكبيرة تستخدم pagination أو filters. |

## 11.2 الاعتمادية

1. لا يسمح بعملية بيع نصف مكتملة.
2. العمليات المترابطة تستخدم transaction.
3. أي فشل في المخزون أو المحاسبة يؤدي إلى rollback.
4. لا يتم تأكيد Offline Sale إلا بعد قبول السيرفر.

## 11.3 سلامة البيانات

1. لا توجد حركة مخزون دون مرجع.
2. لا يوجد قيد محاسبي غير متزن.
3. لا توجد فاتورة مؤكدة دون رقم فريد.
4. لا تتغير الفواتير القديمة بتغير أسعار الصرف.
5. لا يحذف النظام سجلات مالية حساسة حذفًا فعليًا من الواجهة.

## 11.4 الأمان

1. كلمات المرور تخزن Hash لا نصًا صريحًا.
2. حماية JWT/Refresh tokens.
3. تفعيل CORS مضبوط.
4. استخدام Helmet أو ما يعادله.
5. Rate limiting للعمليات الحساسة.
6. Validation لكل المدخلات.
7. منع رفع ملفات خطرة.
8. عدم تخزين أسرار النظام في الكود.
9. تطبيق RBAC في Backend لا في الواجهة فقط.

## 11.5 قابلية الصيانة

1. تقسيم النظام إلى Modules واضحة.
2. استخدام DTOs وValidation.
3. توحيد أسماء الحقول.
4. توحيد ID validation بما يناسب cuid/string.
5. توثيق API.
6. كتابة اختبارات للعمليات الحرجة.

## 11.6 قابلية التشغيل

1. توفير `.env.example`.
2. توفير Dockerfile أو docker-compose إن أمكن.
3. تشغيل migrations بطريقة واضحة.
4. توفير seed data.
5. توفير دليل تشغيل محلي.
6. توفير Release Notes.

# 16. القيود والحدود

1. MVP لا يعني الاكتمال التجاري الكامل.
2. بعض المزايا المتقدمة تؤجل حتى لا تتضخم النسخة.
3. أي تكامل خارجي غير ضروري يؤجل.
4. النظام يجب أن يعطي أرقامًا مالية صادقة، ولو كانت محدودة.
5. عند التعارض بين سرعة الإطلاق وصحة البيانات، تقدم صحة البيانات.
6. لا يجوز إدخال ميزة تكسر رحلة البيع والمخزون والمحاسبة.

# 19. الخلاصة

هذه الوثيقة تحدد المتطلبات الرسمية التي تجعل الزيتون سوفت MVP حقيقيًا لا مجرد واجهات أو تجربة سطحية. جوهر النجاح هو أن تعمل رحلة البيع كاملة من المنتج والمخزون إلى الفاتورة والدفع والقيد المحاسبي والتقرير، مع دعم محدود للمزامنة والنسخ الاحتياطي، وبدون Mock في الشاشات الأساسية.

القاعدة الحاكمة:

> لا نعتمد MVP حتى يثبت النظام أنه يستطيع إدارة عملية بيع ومرتجع وشراء ومخزون ومحاسبة وتقارير من الواجهة إلى قاعدة البيانات بشكل مترابط وموثوق.
