## 1. الغرض من الوثيقة

تهدف هذه الوثيقة إلى تثبيت قواعد الأعمال الحاكمة لنظام **الزيتون سوفت** في نسخة MVP، بحيث تكون مرجعًا رسميًا لكل من:

- فريق التحليل.
- فريق Backend.
- فريق Frontend.
- فريق الاختبار.
- فريق تجربة المستخدم.
- صاحب القرار التجاري.
- أي وكيل AI أو مطور جديد يعمل على المشروع.

هذه الوثيقة لا تصف الواجهات فقط، ولا تكرر المتطلبات الوظيفية، بل تحدد **القواعد التي يجب ألا يخالفها النظام** أثناء تنفيذ العمليات اليومية مثل البيع، المخزون، المحاسبة، العملات، المرتجعات، المشتريات، النسخ الاحتياطي، والمزامنة.

## 3. مبادئ حاكمة

يجب أن يلتزم النظام بالمبادئ التالية:

| الرمز | المبدأ | الشرح |
|---|---|---|
| P-01 | لا عملية مالية بلا أثر قابل للتتبع | أي بيع أو دفع أو مرتجع أو شراء يجب أن يكون له سجل واضح ومصدر معروف. |
| P-02 | لا بيع مؤكد بلا أثر مخزني | عند تأكيد البيع يجب أن يخصم المخزون، إلا في حالات موثقة مثل خدمة غير مخزنية. |
| P-03 | لا أثر مخزني مهم بلا Audit | أي تعديل أو نقل أو خصم أو زيادة مخزون يجب أن يسجل من نفذه ومتى ولماذا. |
| P-04 | لا قيد محاسبي غير متزن | مجموع المدين يجب أن يساوي مجموع الدائن دائمًا. |
| P-05 | لا تعديل مباشر لعملية منشورة | العمليات المؤكدة أو المرحلة تعالج بالإلغاء أو العكس أو المرتجع، لا بالتعديل الصامت. |
| P-06 | سعر الصرف يثبت وقت العملية | تغير سعر الصرف لاحقًا لا يغير الفواتير القديمة. |
| P-07 | الواجهة لا تخفي خطأ جوهريًا | يجب عرض رسالة واضحة عند فشل عملية مهمة. |
| P-08 | كل عملية Offline تبقى معلقة حتى يقبلها السيرفر | لا تصبح العملية Confirmed بمجرد حفظها محليًا. |
| P-09 | لا Mock في MVP النهائي | الشاشات الأساسية يجب أن تعمل على Backend حقيقي وقاعدة بيانات حقيقية. |
| P-10 | البساطة قبل التوسع | أي ميزة لا تخدم رحلة MVP الأساسية تؤجل ولا تكسر النسخة. |

## 4. اصطلاحات ترقيم القواعد

تعتمد القواعد الصيغة التالية:

```txt
BR-{MODULE}-{NUMBER}
```

أمثلة:

```txt
BR-SALES-001
BR-INVENTORY-004
BR-ACCOUNTING-010
```

### 4.1 مستويات الإلزام

| المستوى | المعنى | التعامل |
|---|---|---|
| MUST | إلزامي | لا يقبل النظام مخالفته. |
| SHOULD | مفضل بقوة | ينفذ ما لم يوجد سبب موثق للتأجيل. |
| MAY | اختياري | يمكن تنفيذه أو تأجيله. |

### 4.2 مستويات الخطورة

| المستوى | المعنى | مثال |
|---|---|---|
| Critical | كسر مالي أو أمني أو مخزني | بيع كمية غير متوفرة، قيد غير متزن. |
| High | خلل يؤثر على التشغيل | فشل مزامنة عملية بيع. |
| Medium | خلل مزعج لكنه لا يكسر المال أو المخزون | رسالة خطأ غير واضحة. |
| Low | تحسين أو تفصيل تجميلي | ترتيب عرض عمود. |

| المصطلح | التعريف |

| Default Currency | العملة الافتراضية التي تظهر للمستخدم في العمليات اليومية. |
| Exchange Rate | سعر صرف العملية وقت تنفيذها. |
| Product | المنتج الرئيسي مثل هاتف أو لابتوب. |

| Warehouse | المخزن الذي تحفظ فيه الكميات. |
| Stock Movement | حركة مخزنية مثل بيع، شراء، تعديل، تحويل، مرتجع. |
| Sale Invoice | فاتورة بيع. |
| Purchase Invoice | فاتورة شراء. |
| Payment | دفعة مالية واردة أو صادرة. |
| Credit Note | إشعار دائن ينتج غالبًا من مرتجع أو تصحيح مالي. |
| Journal Entry | قيد محاسبي. |
| Posted | حالة تعني أن العملية أو القيد تم اعتمادها ولا تعدل مباشرة. |
| Draft | حالة مسودة يمكن تعديلها. |
| Voided | حالة إلغاء موثقة. |
| Reversed | حالة عكس أثر مالي بقيد معاكس. |
| Pending Sync | عملية محفوظة محليًا لم يقبلها السيرفر بعد. |
| Idempotency Key | مفتاح يمنع تكرار نفس العملية عند إعادة الإرسال. |

# 6. القواعد العامة للنظام

## BR-GEN-001 — اعتماد مصدر واحد للحقيقة

**المستوى:** MUST  
**الخطورة:** Critical  
يجب أن تكون قاعدة بيانات Backend هي مصدر الحقيقة النهائي للعمليات المؤكدة. لا تعتمد الواجهة أو IndexedDB كمصدر نهائي إلا للعمليات المؤقتة قبل المزامنة.

## BR-GEN-002 — منع استخدام Mock في الشاشات الأساسية

**المستوى:** MUST  
**الخطورة:** Critical  
في نسخة MVP النهائية، يجب ألا تعتمد الشاشات الأساسية على Mock Data، خصوصًا:

- Login.
- Dashboard.
- Settings.
- Products.
- Inventory.
- POS.
- Sales.
- Returns.
- Purchasing.
- Accounting.
- Reports.
- Notifications.
- Sync.
- Backup.

## BR-GEN-003 — توحيد شكل الاستجابة

**المستوى:** MUST  
**الخطورة:** High  
يجب أن تلتزم كل API responses بالشكل الموحد:

```ts
{
  success: boolean;
  data?: any;
  message?: string;
  meta?: {
    page?: number;
    limit?: number;
    total?: number;
    totalPages?: number;
  };
}
```

وفي الأخطاء:

```ts
{
  success: false;
  message: string;
  code: string;
  details?: any;
}
```

## BR-GEN-004 — عدم حذف البيانات الحساسة حذفًا صامتًا

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز حذف العمليات المالية أو المخزنية المؤكدة حذفًا نهائيًا من الواجهة. يجب استخدام حالات مثل:

- `cancelled`
- `voided`
- `reversed`
- `inactive`

حسب نوع السجل.

## BR-GEN-005 — التواريخ والأوقات

**المستوى:** MUST  
**الخطورة:** High  
يجب حفظ التواريخ في قاعدة البيانات بصيغة موحدة، ويفضل UTC، مع عرضها حسب المنطقة الزمنية المحددة في إعدادات الشركة.

## BR-GEN-006 — عدم افتراض إعدادات حرجة

**المستوى:** MUST  
**الخطورة:** Critical  
إذا لم تكن العملة الأساسية، المخزن الافتراضي، أو الحسابات النظامية مضبوطة، يجب منع العمليات التي تعتمد عليها وإظهار رسالة واضحة.

# 7. قواعد المستخدمين والصلاحيات

## BR-AUTH-001 — لا وصول بلا مصادقة

**المستوى:** MUST  
**الخطورة:** Critical  
كل العمليات المحمية يجب أن تتطلب مستخدمًا مصادقًا، باستثناء مسارات عامة محددة صراحة مثل health check أو login.

## BR-AUTH-002 — لا تنفيذ بلا صلاحية

**المستوى:** MUST  
**الخطورة:** Critical  
لا يسمح للمستخدم بتنفيذ أي عملية ما لم يملك الصلاحية المطلوبة مباشرة أو عبر Wildcard معتمد.

مثال:

```txt
products.* يسمح بـ products.create/products.read/products.update/products.delete
```

## BR-AUTH-003 — فصل صلاحيات القراءة عن التعديل

**المستوى:** MUST  
**الخطورة:** High  
امتلاك صلاحية القراءة لا يعني امتلاك صلاحية الإنشاء أو التعديل أو الحذف.

## BR-AUTH-004 — العمليات الحساسة تحتاج صلاحيات خاصة

**المستوى:** MUST  
**الخطورة:** Critical  
العمليات التالية لا تعطى للصراف أو المستخدم العادي افتراضيًا:

- تعديل الإعدادات.
- عكس القيود.
- اعتماد المرتجعات.
- تعديل المخزون يدويًا.
- حذف أو تعطيل مستخدم.
- إنشاء أو تعديل أدوار وصلاحيات.
- تنفيذ استعادة Backup.

## BR-AUTH-005 — تعطيل المستخدم لا يحذف سجله

**المستوى:** MUST  
**الخطورة:** High  
عند تعطيل مستخدم يجب منع دخوله مستقبلًا مع بقاء سجلاته التاريخية مرتبطة باسمه أو معرفه.

## BR-AUTH-006 — تسجيل العمليات الحساسة

**المستوى:** MUST  
**الخطورة:** High  
كل عملية حساسة يجب أن تسجل في Audit Log، ومنها:

- Login failed repeated attempts.
- تغيير كلمة مرور.
- تغيير صلاحيات.
- اعتماد أو إلغاء فاتورة.
- تعديل مخزون.
- عكس قيد.
- تغيير إعدادات العملة أو سعر الصرف.

# 8. قواعد الإعدادات

## BR-SETTINGS-001 — وجود إعدادات شركة أساسية

**المستوى:** MUST  
**الخطورة:** High  
يجب أن يحتوي النظام على إعدادات شركة أساسية قبل التشغيل الفعلي، وتشمل:

- اسم الشركة.
- العملة الأساسية.
- اللغة.
- المنطقة الزمنية.
- المخزن الافتراضي إن تم اعتماده.
- إعدادات الفواتير الأساسية.

## BR-SETTINGS-002 — منع حذف العملة الأساسية من الإعدادات

**المستوى:** MUST  
**الخطورة:** Critical  
لا يجوز حذف أو تعطيل العملة الأساسية طالما توجد عمليات مالية مرتبطة بها.

## BR-SETTINGS-003 — تغيير الإعدادات لا يعيد كتابة التاريخ

**المستوى:** MUST  
**الخطورة:** Critical  
تغيير اسم الشركة أو شعارها أو إعدادات الفواتير لا يجب أن يغير الأثر المالي أو المخزني للعمليات السابقة.

## BR-SETTINGS-004 — إعدادات النسخ الاحتياطي محمية

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز تعديل إعدادات النسخ الاحتياطي إلا من مدير النظام أو دور مخول صراحة.

# 9. قواعد الفروع والمخازن

## BR-ORG-001 — وجود مخزن واحد على الأقل

**المستوى:** MUST  
**الخطورة:** High  
لا يمكن تشغيل المخزون أو البيع دون وجود مخزن واحد نشط على الأقل.

## BR-ORG-002 — لا حذف لمخزن له حركات

**المستوى:** MUST  
**الخطورة:** Critical  
إذا كان للمخزن حركات مخزنية أو فواتير مرتبطة، لا يجوز حذفه حذفًا نهائيًا. يمكن تعطيله فقط.

## BR-ORG-003 — المخزن المعطل لا يستخدم في عمليات جديدة

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز إنشاء بيع أو شراء أو تحويل مخزون جديد على مخزن معطل.

## BR-ORG-004 — التحويل بين المخازن يحتاج مخزنين مختلفين

**المستوى:** MUST  
**الخطورة:** Medium  
لا يجوز إنشاء تحويل مخزني من مخزن إلى نفس المخزن.

# 10. قواعد العملات وأسعار الصرف

## BR-CUR-001 — وجود عملة أساسية واحدة فقط

**المستوى:** MUST  
**الخطورة:** Critical  
يجب أن يكون للنظام عملة أساسية واحدة فقط في أي وقت.

## BR-CUR-002 — كل عملية مالية تحفظ العملة وسعر الصرف

**المستوى:** MUST  
**الخطورة:** Critical  
كل فاتورة أو دفعة أو قيد مالي يجب أن يحفظ:

```txt
currencyId
exchangeRate
baseCurrencyId
amount
baseAmount
```

## BR-CUR-003 — لا تغيير للفواتير القديمة عند تغير سعر الصرف

**المستوى:** MUST  
**الخطورة:** Critical  
تحديث سعر الصرف لا يعيد حساب العمليات السابقة.

## BR-CUR-004 — البيع بعملة غير أساسية يتطلب سعر صرف

**المستوى:** MUST  
**الخطورة:** Critical  
لا يجوز تأكيد فاتورة بعملة غير العملة الأساسية إذا لم يكن سعر الصرف متوفرًا وقت العملية.

## BR-CUR-005 — التقارير المالية تعرض بالعملة الأساسية

**المستوى:** MUST  
**الخطورة:** High  
يجب أن تعتمد تقارير الربح والخسارة، ميزان المراجعة، أرصدة الحسابات، ولوحة المعلومات المالية على العملة الأساسية.

## BR-CUR-006 — منع سعر الصرف الصفري أو السالب

**المستوى:** MUST  
**الخطورة:** Critical  
لا يقبل النظام سعر صرف يساوي صفرًا أو أقل من صفر.

## BR-CUR-007 — يمكن عرض الفاتورة بعملتها الأصلية

**المستوى:** SHOULD  
**الخطورة:** Medium  
ينبغي أن تعرض الفاتورة العملة الأصلية المستخدمة في البيع، إلى جانب القيمة المحولة للعملة الأساسية عند الحاجة.

# 11. قواعد المنتجات والمتغيرات والباركود

## BR-PROD-001 — المنتج لا يباع ما لم يكن نشطًا

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز بيع منتج أو متغير منتج غير نشط.

## BR-PROD-002 — SKU أو Barcode يجب أن يكون فريدًا عند استخدامه

**المستوى:** MUST  
**الخطورة:** High  
إذا تم إدخال SKU أو Barcode، يجب ألا يتكرر لنفس نطاق الشركة/النظام.

## BR-PROD-003 — المنتج المخزني يجب أن يرتبط بالمخزون

**المستوى:** MUST  
**الخطورة:** High  
أي منتج محدد كمنتج مخزني يجب أن تكون حركاته مرتبطة بجدول المخزون.

## BR-PROD-004 — المنتج غير المخزني لا يخصم من المخزون

**المستوى:** MUST  
**الخطورة:** Medium  
إذا دعم النظام منتجات غير مخزنية لاحقًا، فلا يجوز إنشاء حركات مخزون لها.

## BR-PROD-005 — لا حذف نهائي لمنتج له حركات

**المستوى:** MUST  
**الخطورة:** High  
إذا كان المنتج مرتبطًا بفواتير أو حركات مخزون، لا يجوز حذفه نهائيًا. يستخدم التعطيل بدل الحذف.

## BR-PROD-006 — السعر لا يكون سالبًا

**المستوى:** MUST  
**الخطورة:** Critical  
لا يقبل النظام سعر بيع أو تكلفة شراء سالبة.

## BR-PROD-007 — صورة المنتج ليست شرطًا للبيع

**المستوى:** SHOULD  
**الخطورة:** Low  
عدم وجود صورة للمنتج لا يمنع البيع، لكنه لا يمنع النظام من عرض صورة افتراضية.

# 12. قواعد التسعير والخصومات والعروض

## BR-PRICE-001 — السعر النهائي لا يكون سالبًا

**المستوى:** MUST  
**الخطورة:** Critical  
بعد تطبيق الخصومات، لا يجوز أن يصبح صافي سعر السطر أو الفاتورة أقل من صفر.

## BR-PRICE-002 — الخصم يحتاج صلاحية إذا تجاوز الحد المسموح

**المستوى:** SHOULD  
**الخطورة:** Medium  
يمكن تحديد حد خصم للصراف، وأي خصم أكبر منه يحتاج صلاحية مدير.

## BR-PRICE-003 — الخصم يوثق في الفاتورة

**المستوى:** MUST  
**الخطورة:** High  
أي خصم على السطر أو الفاتورة يجب أن يحفظ في الفاتورة ولا يحسب مؤقتًا فقط في الواجهة.

## BR-PRICE-004 — العروض لا تطبق إذا كانت غير نشطة أو خارج التاريخ

**المستوى:** SHOULD  
**الخطورة:** Medium  
إذا تم تفعيل العروض في MVP أو بعده، يجب ألا يطبق النظام عرضًا غير نشط أو منتهي الصلاحية.

## BR-PRICE-005 — أولوية الخصومات يجب أن تكون واضحة

**المستوى:** SHOULD  
**الخطورة:** Medium  
إذا اجتمع خصم يدوي وعرض تلقائي، يجب تحديد السياسة: هل يجتمعان، أم يطبق الأعلى، أم يمنع الجمع.

> قرار MVP المقترح: السماح بخصم يدوي بسيط على السطر أو الفاتورة، وتأجيل محرك العروض المتقدم إن لم يكن جاهزًا.

# 13. قواعد المخزون

## BR-INV-001 — لا بيع بدون تحقق من الكمية

**المستوى:** MUST  
**الخطورة:** Critical  
قبل تأكيد البيع، يجب التحقق من توفر الكمية المطلوبة في المخزن المحدد.

## BR-INV-002 — منع المخزون السالب افتراضيًا

**المستوى:** MUST  
**الخطورة:** Critical  
في MVP، لا يسمح بالمخزون السالب إلا إذا تم تفعيل سياسة واضحة لاحقًا، وهذا غير مقترح للنسخة الأولى.

## BR-INV-003 — كل حركة مخزون لها نوع ومرجع

**المستوى:** MUST  
**الخطورة:** High  
كل حركة مخزون يجب أن تحفظ:

```txt
movementType
productVariantId
warehouseId
quantity
referenceType
referenceId
createdBy
createdAt
```

## BR-INV-004 — البيع ينقص المخزون

**المستوى:** MUST  
**الخطورة:** Critical  
عند تأكيد فاتورة بيع لمنتج مخزني، يجب إنشاء حركة مخزون سالبة.

## BR-INV-005 — الشراء يزيد المخزون

**المستوى:** MUST  
**الخطورة:** Critical  
عند اعتماد فاتورة شراء لمنتج مخزني، يجب إنشاء حركة مخزون موجبة.

## BR-INV-006 — المرتجع يزيد المخزون وفق سياسة الحالة

**المستوى:** MUST  
**الخطورة:** Critical  
عند مرتجع بيع، لا يعود المنتج إلى المخزون القابل للبيع إلا إذا كانت حالته صالحة للبيع.

حالات مقترحة:

| الحالة | الأثر |
|---|---|
| Sellable | يعود للمخزون المتاح. |
| Damaged | يسجل في مخزون تالف أو لا يعود للمخزون المتاح. |
| Needs Review | يبقى معلقًا حتى المراجعة. |

## BR-INV-007 — التعديل اليدوي يحتاج سببًا

**المستوى:** MUST  
**الخطورة:** High  
أي تعديل يدوي للمخزون يجب أن يتضمن سببًا واضحًا وأن يسجل في Audit Log.

## BR-INV-008 — التحويل بين المخازن ينشئ حركتين

**المستوى:** MUST  
**الخطورة:** High  
تحويل المخزون من مخزن إلى آخر يجب أن ينشئ:

- حركة خروج من المخزن المصدر.
- حركة دخول إلى المخزن الهدف.

ويجب أن تنفذا داخل Transaction واحدة.

## BR-INV-009 — لا حركة مخزون بلا Transaction عند العمليات المركبة

**المستوى:** MUST  
**الخطورة:** Critical  
عمليات البيع، الشراء، المرتجع، والتحويل يجب أن تنفذ حركات المخزون داخل نفس Database Transaction مع العملية الأصلية.

## BR-INV-010 — تكلفة المخزون تعتمد المتوسط المرجح في MVP

**المستوى:** SHOULD  
**الخطورة:** High  
تعتمد نسخة MVP طريقة **Weighted Average Cost** لحساب تكلفة المخزون، ما لم يقرر الفريق خلاف ذلك بوثيقة منفصلة.

## BR-INV-011 — Low Stock يعتمد على حد أدنى واضح

**المستوى:** SHOULD  
**الخطورة:** Medium  
تنبيه انخفاض المخزون يظهر عندما تكون الكمية المتاحة أقل من أو تساوي الحد الأدنى المحدد للمنتج أو المتغير.

# 14. قواعد نقطة البيع POS

## BR-POS-001 — POS لا يعرض منتجات غير قابلة للبيع

**المستوى:** MUST  
**الخطورة:** High  
يجب ألا تعرض شاشة POS المنتجات غير النشطة أو غير القابلة للبيع.

## BR-POS-002 — البحث يدعم الاسم والباركود/SKU

**المستوى:** SHOULD  
**الخطورة:** Medium  
ينبغي أن يدعم POS البحث بالاسم والباركود وSKU لتسريع البيع.

## BR-POS-003 — السلة لا تقبل كمية صفرية أو سالبة

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز إضافة صنف إلى السلة بكمية صفر أو أقل.

## BR-POS-004 — تأكيد البيع مسؤولية Backend

**المستوى:** MUST  
**الخطورة:** Critical  
لا تعتمد الواجهة وحدها على حسابات السلة. Backend يجب أن يعيد التحقق من السعر، الكمية، الصلاحية، العملة، والمخزون قبل التأكيد.

## BR-POS-005 — البيع Offline لا يصبح مؤكدًا مباشرة

**المستوى:** MUST  
**الخطورة:** Critical  
أي بيع يتم Offline يجب أن يكون `Pending Sync` حتى يقبله السيرفر.

## BR-POS-006 — منع تكرار البيع عند إعادة المحاولة

**المستوى:** MUST  
**الخطورة:** Critical  
كل عملية POS، خصوصًا Offline، يجب أن تستخدم `idempotencyKey` لمنع تكرار الفاتورة عند إعادة الإرسال.

## BR-POS-007 — لا إغلاق شاشة البيع قبل حفظ النتيجة

**المستوى:** SHOULD  
**الخطورة:** Medium  
يجب أن تعرض الواجهة حالة العملية بوضوح: جاري المعالجة، نجحت، فشلت، أو محفوظة للمزامنة.

# 15. قواعد فواتير البيع

## BR-SALES-001 — حالات فاتورة البيع

**المستوى:** MUST  
**الخطورة:** High

```txt
DRAFT
CONFIRMED
PAID
PARTIALLY_PAID
CANCELLED
RETURNED
PARTIALLY_RETURNED
```

يمكن تبسيطها في الواجهة، لكن يجب ألا يختلط الأثر الداخلي.

## BR-SALES-002 — الفاتورة المؤكدة لا تعدل مباشرة

**المستوى:** MUST  
**الخطورة:** Critical  
بعد تأكيد الفاتورة، لا يجوز تعديل الأصناف أو الكميات أو الأسعار مباشرة. المعالجة تكون عبر:

- إلغاء قبل الترحيل النهائي إن كانت السياسة تسمح.
- مرتجع.
- Credit Note.
- قيد عكسي عند الحاجة.

## BR-SALES-003 — الفاتورة تحفظ الإجماليات المحسوبة

**المستوى:** MUST  
**الخطورة:** High  
يجب حفظ:

```txt
subtotal
discountTotal
taxTotal إن وجدت
grandTotal
paidAmount
remainingAmount
currencyId
exchangeRate
baseAmount
```

## BR-SALES-004 — لا تأكيد لفاتورة فارغة

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز تأكيد فاتورة بيع لا تحتوي على أي سطر.

## BR-SALES-005 — سعر السطر يحفظ وقت البيع

**المستوى:** MUST  
**الخطورة:** Critical  
تغيير سعر المنتج لاحقًا لا يغير فواتير البيع السابقة.

## BR-SALES-006 — كل سطر فاتورة يحفظ بيانات كافية تاريخيًا

**المستوى:** SHOULD  
**الخطورة:** Medium  
ينبغي أن يحفظ سطر الفاتورة اسم المنتج أو نسخة منه وقت البيع بجانب `productVariantId`، حتى تبقى الفاتورة مفهومة إذا تغير اسم المنتج لاحقًا.

## BR-SALES-007 — فشل خطوة في البيع يؤدي إلى Rollback

**المستوى:** MUST  
**الخطورة:** Critical  
إذا فشل أي جزء من عملية البيع المؤكدة، مثل خصم المخزون أو إنشاء الدفعة أو القيد المحاسبي، يجب إلغاء العملية كلها داخل Transaction واحدة.

**المستوى:** MUST  
**الخطورة:** Critical  
لا يجوز إنشاء مرتجع من فاتورة غير مؤكدة أو ملغاة.

## BR-RET-002 — لا إرجاع لكمية أكبر من المباعة

**المستوى:** MUST  
**الخطورة:** Critical  
يجب أن يمنع النظام إرجاع كمية أكبر من الكمية الصافية القابلة للإرجاع.

**المستوى:** MUST  
**الخطورة:** Medium

- عيب.
- خطأ بيع.

**المستوى:** MUST  
**الخطورة:** Critical

أي Credit Note يجب أن يرتبط بفاتورة أو مرتجع أو سبب مالي موثق.

**المستوى:** MUST  
**الخطورة:** Medium  
إذا تم إرجاع بعض الأصناف فقط، يجب أن تصبح الفاتورة `PARTIALLY_RETURNED` لا `RETURNED` بالكامل.

# 20. قواعد المحاسبة العامة GL

## BR-ACC-001 — وجود حسابات نظامية أساسية

**المستوى:** MUST  
**الخطورة:** Critical  
يجب أن توجد حسابات نظامية أساسية في Seed، مثل:

- Cash.
- Accounts Receivable.
- Inventory.
- Accounts Payable.
- Sales Revenue.
- Sales Returns أو Contra Revenue عند الحاجة.
- Cost of Goods Sold.
- Inventory Adjustment.
- Equity/Opening Balance إن احتاج النظام.

## BR-ACC-002 — لا قيد غير متزن

**المستوى:** MUST  
**الخطورة:** Critical  
لا يقبل النظام أي Journal Entry يكون فيه مجموع المدين لا يساوي مجموع الدائن.

## BR-ACC-003 — كل قيد له مصدر أو سبب

**المستوى:** MUST  
**الخطورة:** High  
كل قيد يجب أن يحتوي:

```txt
sourceType
sourceId
memo
createdBy
postedAt إن وجد
```

## BR-ACC-004 — القيود التلقائية لا تعدل يدويًا بصمت

**المستوى:** MUST  
**الخطورة:** Critical  
القيد الناتج من بيع أو شراء أو مرتجع لا يعدل يدويًا بدون سياسة تصحيح واضحة. التصحيح يكون بقيد عكسي أو عملية مصدر جديدة.

## BR-ACC-005 — القيد المنشور لا يعدل مباشرة

**المستوى:** MUST  
**الخطورة:** Critical  
إذا صار القيد `POSTED`، لا يسمح بتعديل سطوره. إذا احتاج تصحيحًا، يستخدم `REVERSE` أو قيد تصحيح.

## BR-ACC-006 — البيع النقدي ينشئ قيدًا للإيراد

**المستوى:** MUST  
**الخطورة:** Critical  
عند بيع نقدي:

```txt
Debit: Cash
Credit: Sales Revenue
```

## BR-ACC-007 — البيع الآجل ينشئ ذمة مدينة

**المستوى:** MUST  
**الخطورة:** High  
عند بيع آجل:

```txt
Debit: Accounts Receivable
Credit: Sales Revenue
```

## BR-ACC-008 — تكلفة البضاعة تسجل عند البيع إن توفرت التكلفة

**المستوى:** MUST  
**الخطورة:** Critical  
عند بيع منتج مخزني بتكلفة معروفة:

```txt
Debit: Cost of Goods Sold
Credit: Inventory
```

## BR-ACC-009 — الشراء النقدي ينشئ قيد مخزون مقابل نقدية

**المستوى:** MUST  
**الخطورة:** High  
عند شراء نقدي:

```txt
Debit: Inventory
Credit: Cash
```

## BR-ACC-010 — الشراء الآجل ينشئ ذمة دائنة

**المستوى:** MUST  
**الخطورة:** High  
عند شراء آجل:

```txt
Debit: Inventory
Credit: Accounts Payable
```

## BR-ACC-011 — دفع المورد يعكس الذمة الدائنة

**المستوى:** MUST  
**الخطورة:** High  
عند دفع مبلغ للمورد:

```txt
Debit: Accounts Payable
Credit: Cash
```

## BR-ACC-012 — تحصيل العميل يعكس الذمة المدينة

**المستوى:** MUST  
**الخطورة:** High  
عند تحصيل مبلغ من عميل:

```txt
Debit: Cash
Credit: Accounts Receivable
```

## BR-ACC-013 — المرتجع يعكس الإيراد وتكلفة البضاعة

**المستوى:** MUST  
**الخطورة:** Critical  
مرتجع البيع يجب أن يعكس أثر الإيراد والدفع/الذمة، ويعكس تكلفة البضاعة إذا عاد المنتج للمخزون القابل للبيع.

## BR-ACC-014 — تعديل المخزون له أثر محاسبي

**المستوى:** SHOULD  
**الخطورة:** High  
إذا تم تعديل المخزون يدويًا، يجب أن يسجل أثره على حساب Inventory Adjustment أو حساب مماثل.

## BR-ACC-015 — لا استخدام حساب غير نشط في قيد جديد

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز إنشاء قيد جديد على حساب معطل.

## BR-ACC-016 — التقارير المحاسبية تعتمد على القيود المنشورة

**المستوى:** MUST  
**الخطورة:** High  
ميزان المراجعة، دفتر الأستاذ، والربح والخسارة يجب أن تعتمد على القيود المعتمدة/المنشورة، لا على حسابات مؤقتة من الواجهة.

**المستوى:** MUST  
**الخطورة:** Medium  
فشل إنشاء إشعار غير حرج لا يجب أن يكسر عملية بيع صحيحة، إلا إذا قرر الفريق أن الإشعار جزء إلزامي من transaction.

## BR-NOTIF-004 — قراءة الإشعار لا تحذف تاريخه

**المستوى:** MUST  
**الخطورة:** Low  
عند تعليم إشعار كمقروء، يجب الاحتفاظ به في السجل ما لم توجد سياسة تنظيف واضحة.

# 23. قواعد Offline/Sync

## BR-SYNC-001 — السيرفر هو الحكم النهائي

**المستوى:** MUST  
**الخطورة:** Critical  
أي عملية Offline لا تعتبر مؤكدة حتى يقبلها Backend.

## BR-SYNC-002 — كل عملية Offline لها Idempotency Key

**المستوى:** MUST  
**الخطورة:** Critical  
يجب أن تحتوي كل عملية محفوظة للمزامنة على مفتاح يمنع تكرارها.

## BR-SYNC-003 — لا تأكيد لبيع Offline إذا لم يعد المخزون كافيًا

**المستوى:** MUST  
**الخطورة:** Critical  
عند مزامنة بيع Offline، يجب أن يعيد Backend التحقق من المخزون. إذا لم يعد كافيًا، ترفض العملية أو تدخل حالة تعارض.

## BR-SYNC-004 — حالات المزامنة واضحة

**المستوى:** MUST  
**الخطورة:** High  
يجب دعم حالات مثل:

```txt
PENDING
SYNCING
SYNCED
FAILED
CONFLICT
```

## BR-SYNC-005 — التعارض لا يعالج بصمت

**المستوى:** MUST  
**الخطورة:** Critical  
إذا حدث Conflict، يجب عرضه للمستخدم المخول ولا يتم تعديله تلقائيًا دون سجل.

## BR-SYNC-006 — المزامنة لا تتجاوز صلاحيات المستخدم

**المستوى:** MUST  
**الخطورة:** High  
إذا فقد المستخدم صلاحية عملية قبل مزامنتها، يجب أن يقرر Backend قبولها أو رفضها وفق السياسة، ولا تعتمد الواجهة على الصلاحية القديمة.

## BR-SYNC-007 — Initial Sync محدود وعملي

**المستوى:** SHOULD  
**الخطورة:** Medium  
في MVP، يجب أن يقتصر Initial Sync على البيانات الضرورية للبيع والعمل الأساسي، وليس كامل النظام إذا كان ذلك مكلفًا.

# 24. قواعد النسخ الاحتياطي والاستعادة

## BR-BACKUP-001 — إنشاء Backup يدوي ضمن MVP

**المستوى:** MUST  
**الخطورة:** High  
يجب أن يدعم النظام إنشاء سجل Backup يدوي على الأقل في MVP، حسب التصميم المعتمد.

## BR-BACKUP-002 — كل Backup له Metadata

**المستوى:** MUST  
**الخطورة:** High  
كل نسخة احتياطية يجب أن تحفظ:

```txt
backupId
createdBy
createdAt
status
size إن توفر
location إن توفر
notes
```

## BR-BACKUP-003 — الاستعادة عملية عالية الخطورة

**المستوى:** MUST  
**الخطورة:** Critical  
استعادة Backup لا تنفذ إلا بصلاحية مدير النظام وبعد تحذير واضح، ويفضل تأجيل الاستعادة الكاملة في MVP إن لم تكن مختبرة.

## BR-BACKUP-004 — فشل Backup يسجل بوضوح

**المستوى:** MUST  
**الخطورة:** High  
إذا فشل النسخ الاحتياطي، يجب تسجيل السبب وإظهار حالة فشل لا تجاهلها.

# 25. قواعد التخزين والملفات

## BR-STOR-001 — رفع الملفات يتم عبر Storage Module

**المستوى:** MUST  
**الخطورة:** High  
يجب أن تمر عمليات رفع الصور والشعارات عبر وحدة التخزين المعتمدة، لا عبر مسارات عشوائية.

## BR-STOR-002 — التحقق من نوع وحجم الملف

**المستوى:** MUST  
**الخطورة:** High  
يجب التحقق من نوع الملف وحجمه قبل قبوله، خصوصًا صور المنتجات وشعار الشركة.

## BR-STOR-003 — لا تنفيذ لملفات مرفوعة

**المستوى:** MUST  
**الخطورة:** Critical  
الملفات المرفوعة لا يجوز تنفيذها أو حفظها بطريقة تسمح بتشغيل كود.

## BR-STOR-004 — حذف الملف لا يكسر التاريخ

**المستوى:** SHOULD  
**الخطورة:** Medium  
إذا حذفت صورة منتج، لا يجب أن تتعطل الفواتير التاريخية أو البيانات الأساسية.

## BR-STOR-005 — شعار الشركة لا يؤثر على العمليات القديمة

**المستوى:** MUST  
**الخطورة:** Low  
تغيير شعار الشركة يغير العرض المستقبلي، لكنه لا يغير الأثر المالي أو المخزني.

# 26. قواعد Audit Logs

## BR-AUDIT-001 — تسجيل من ومتى وماذا

**المستوى:** MUST  
**الخطورة:** High  
كل Audit Log يجب أن يحفظ:

```txt
actorUserId
action
entityType
entityId
beforeSnapshot إن لزم
afterSnapshot إن لزم
createdAt
ip/userAgent إن توفر
```

## BR-AUDIT-002 — Audit لا يعتمد على الواجهة

**المستوى:** MUST  
**الخطورة:** High  
يجب إنشاء Audit Logs من Backend، لا من Frontend فقط.

## BR-AUDIT-003 — العمليات المالية والمخزنية الحساسة مسجلة

**المستوى:** MUST  
**الخطورة:** Critical  
يجب تسجيل:

- تأكيد البيع.
- إلغاء البيع.
- المرتجع.
- تعديل المخزون.
- تحويل المخزون.
- إنشاء أو عكس قيد.
- تغيير سعر الصرف.
- تغيير صلاحيات.
- تنفيذ Backup أو Restore.

## BR-AUDIT-004 — لا حذف سهل لـ Audit Logs

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز حذف Audit Logs من الواجهة العادية. تنظيفها إن وجد يكون بسياسة إدارية منفصلة.

# 27. قواعد الأمان والتحقق

## BR-SEC-001 — التحقق من المدخلات في Backend

**المستوى:** MUST  
**الخطورة:** Critical  
كل مدخلات المستخدم يجب التحقق منها في Backend، حتى لو تحققت منها الواجهة.

## BR-SEC-002 — استخدام ID موحد

**المستوى:** MUST  
**الخطورة:** High  
إذا اعتمد النظام `cuid/string` فلا يجوز استخدام `@IsUUID()` في DTOs لهذه الحقول. يجب استخدام تحقق موحد مثل `IsEntityId` أو قواعد string واضحة.

## BR-SEC-003 — حماية الأسرار

**المستوى:** MUST  
**الخطورة:** Critical  
لا تحفظ مفاتيح R2 أو JWT secrets أو كلمات مرور قاعدة البيانات في الكود أو المستودع.

## BR-SEC-004 — سياسة كلمات المرور

**المستوى:** SHOULD  
**الخطورة:** Medium  
ينبغي فرض حد أدنى معقول لكلمات المرور، ومنع كلمات المرور الضعيفة جدًا.

## BR-SEC-005 — Rate Limit على المسارات الحساسة

**المستوى:** SHOULD  
**الخطورة:** Medium  
يفضل تطبيق Rate Limit على Login ومسارات حساسة أخرى لمنع المحاولات المتكررة.

## BR-SEC-006 — CORS مضبوط حسب البيئة

**المستوى:** MUST  
**الخطورة:** High  
لا يجوز فتح CORS بشكل عشوائي في الإنتاج.

# 28. قواعد الأخطاء ورسائل النظام

## BR-ERR-001 — لكل خطأ كود واضح

**المستوى:** MUST  
**الخطورة:** High  
كل خطأ متوقع يجب أن يرجع `code` واضحًا يمكن للواجهة التعامل معه.

أمثلة:

| الكود | المعنى |
|---|---|
| AUTH_INVALID_CREDENTIALS | بيانات الدخول غير صحيحة. |
| PERMISSION_DENIED | لا توجد صلاحية. |
| STOCK_INSUFFICIENT | المخزون غير كافٍ. |
| CURRENCY_RATE_MISSING | سعر الصرف غير موجود. |
| JOURNAL_NOT_BALANCED | القيد غير متزن. |
| ENTITY_NOT_FOUND | السجل غير موجود. |
| VALIDATION_ERROR | خطأ تحقق من البيانات. |
| SYNC_CONFLICT | تعارض أثناء المزامنة. |
| BACKUP_FAILED | فشل النسخ الاحتياطي. |

## BR-ERR-002 — لا كشف معلومات حساسة في الخطأ

**المستوى:** MUST  
**الخطورة:** Critical  
لا يجوز عرض تفاصيل تقنية حساسة للمستخدم النهائي مثل stack trace أو secrets أو SQL queries.

## BR-ERR-003 — الأخطاء المالية والمخزنية لا تتجاهل

**المستوى:** MUST  
**الخطورة:** Critical  
إذا فشل الخصم من المخزون أو إنشاء القيد المحاسبي، لا يجوز إكمال البيع كأنه ناجح.

## BR-ERR-004 — رسائل الواجهة مفهومة

**المستوى:** SHOULD  
**الخطورة:** Medium  
ينبغي تحويل أكواد الأخطاء إلى رسائل عربية واضحة للمستخدم.

# 29. جداول قرارات مختصرة

## 29.1 قرار تأكيد البيع

| الشرط | القرار |
|---|---|
| المستخدم غير مصادق | رفض |
| لا يملك `sales.create` | رفض |
| الفاتورة بلا أصناف | رفض |
| منتج غير نشط | رفض |
| كمية غير كافية | رفض |
| العملة بلا سعر صرف | رفض |
| الحسابات النظامية ناقصة | رفض |
| كل الشروط صحيحة | تأكيد البيع داخل Transaction |

## 29.2 قرار إرجاع صنف

| الشرط | القرار |
|---|---|
| الفاتورة غير مؤكدة | رفض |
| الكمية أكبر من المتاح للإرجاع | رفض |
| لا يوجد سبب مرتجع | رفض أو تحذير حسب السياسة |
| المنتج صالح للبيع | يرجع للمخزون المتاح |
| المنتج تالف | لا يرجع للمخزون المتاح |
| العملية صحيحة | إنشاء مرتجع + Credit Note + أثر محاسبي |

## 29.3 قرار مزامنة بيع Offline

| الشرط | القرار |
|---|---|
| idempotencyKey مكرر ومقبول سابقًا | إرجاع نفس النتيجة بدون تكرار |
| المستخدم غير صالح | رفض |
| المخزون غير كافٍ وقت المزامنة | Conflict/رفض |
| سعر الصرف غير صالح | رفض |
| البيانات صحيحة | تأكيد العملية وإنشاء آثارها |

## 29.4 قرار تعديل قيد محاسبي

| الحالة | القرار |
|---|---|
| Draft | يمكن تعديله بصلاحية مناسبة |
| Posted | لا يعدل مباشرة |
| Posted وفيه خطأ | إنشاء Reverse أو قيد تصحيح |
| مرتبط بفاتورة | يعالج من مصدره لا بتعديل يدوي صامت |

# 32. قائمة القواعد الحرجة التي لا يجوز تجاوزها

هذه أهم قواعد يجب تنفيذها قبل اعتبار MVP قابلًا للتجربة:

1. لا بيع بدون مخزون كافٍ.
2. لا بيع مؤكد بلا خصم مخزون.
3. لا بيع مؤكد بلا أثر محاسبي عند تفعيل المحاسبة.
4. لا قيد محاسبي غير متزن.
5. لا عملية مالية بعملة أجنبية بلا سعر صرف محفوظ.
6. لا تعديل مباشر لفاتورة أو قيد منشور.
7. لا مرتجع لكمية أكبر من المباعة.
8. لا Offline sale يصبح مؤكدًا قبل قبول السيرفر.
9. لا عملية Offline بلا idempotency key.
10. لا حذف نهائي لسجلات مالية أو مخزنية لها أثر تاريخي.
11. لا استخدام Mock في شاشات MVP الأساسية.
12. لا صلاحية حساسة لمستخدم غير مخول.
13. لا أسرار محفوظة في الكود.
14. لا Backup أو Restore بلا صلاحية وسجل.
15. لا Dashboard يعرض أرقامًا مالية غير مبنية على بيانات موثوقة.

# 33. ما يؤجل بعد MVP

حتى لا يتضخم النطاق، تؤجل القواعد التفصيلية التالية إلى ما بعد MVP ما لم يقرر الفريق خلاف ذلك:

1. محرك عروض وتسويق متقدم.
2. ضرائب متعددة ومعقدة.
3. إدارة اشتراكات SaaS كاملة.
4. بوابات دفع خارجية.
5. تكامل WhatsApp/SMS.
6. ذكاء اصطناعي متقدم في التحليل أو التنبؤ.
7. FIFO/LIFO إذا لم يعتمد الفريق غير المتوسط المرجح.
8. صلاحيات فرعية شديدة التفصيل لكل زر.
9. Multi-tenant متقدم إن لم يكن مكتملًا معماريًا.
10. استعادة Backup ذاتية كاملة من الواجهة إن لم تختبر جيدًا.

# 34. خاتمة

هذه الوثيقة هي مرجع قواعد الأعمال لنسخة MVP من **الزيتون سوفت**.  
أي تنفيذ يخالف قاعدة Critical يجب اعتباره عيبًا مانعًا قبل الإطلاق الداخلي.  
وأي توسع جديد يجب أن يراجع أمام هذه الوثيقة و`MVP_SCOPE.md` قبل إدخاله في خطة التنفيذ.

الهدف ليس بناء نظام ضخم بسرعة، بل بناء نظام موثوق، صادق في أرقامه، واضح في عملياته، ويصلح للتجربة الحقيقية داخل محلات الإلكترونيات الصغيرة والمتوسطة.
